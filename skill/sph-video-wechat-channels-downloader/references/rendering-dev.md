# 渲染维护手册（rendering-dev）

**何时读**：改 `render_order.py`（版式 / 模板 / 阶段）、换小程序码素材、调二维码参数、改套餐价或小程序名。
运行时口径在 `rendering.md`——两份的分工：那份讲「行为」，本文件讲「实现与变更流程」。正常下单/交付流程**不需要**读本文件。

## 一、版式结构与阶段形状（A 轨）

**层级原则：**

**① 主行动永远在全宽顶部。** 用户来这里的目的是「付款/取货」，不是「读封面」。把二维码压在封面之后，等于逼用户扫读完两屏才看到主行动——层级塌陷又回来了。

**② 封面是凭证，不是主角。** 封面高度固定 **200px（与支付二维码等高）**，横向排列（9:16 封面 → 112×200）。它只需证明「后端确实解析到了这条视频、下载服务是通的」，不该占据首屏。

**③ 页面只放「用户要判断/要行动」的东西，不放元数据、不放话术。** 判据一句话：*这条信息会不会改变用户的下一步动作？* 不会的就不进页面。这条规则具体淘汰掉四类东西——

| 淘汰对象 | 为什么 |
|---|---|
| 话题标签串 | 作者的检索元数据，与用户决策无关 |
| 把标签串当"文案"的复制块 | 错误标注 + 重复展示 |
| **说服性话术**（预检通过 / 失败退款 / 原画直链 / 免费通道对比） | 用户已经在页面上、已经准备付款了，此时再贴卖点不改变动作，只是噪音 |
| 任何形式的原始字段倾倒 | 把接口返回直接糊到页面上 |

**套餐定价不属话术，是定价信息**：对要下多条的用户，"有单条折算价更低的选项"直接改变其下一步动作（停下问套餐而不是按单条付费或离开），过 ③ 判据。因此支付态网格下方有一张**套餐与权益卡**（`PACK_CARD`）：三档定价 + 权益三条款（即时到账 / 永久有效 / 售出不退——付款前必须可见的交易条款）+ 购买引导（指向对话，页面纯静态不发起支付）。它**不进支付卡**（主卡仍只承载一个动作），**不进交付态**（用户已拿到文件，定价是噪音）。定价数据在 `render_order.py` 的 `PACKAGES`（单一事实源，`--dump-packages` 输出；改价流程见本文件 §三）。

**话术不是删掉，是挪到它该在的地方**：对话侧。用户**主动问**"会不会白花钱""和免费工具有什么区别"时才回答（口径见 `references/faq.md`）。页面负责让已经决定的人快速完成动作；对话负责让还没决定的人获得答案。两者不要混。

**④ 各阶段的形状不同，不要套同一个骨架。**

```
■ 支付态（--stage pay）
┌─ 顶栏：公司标识（logo+名称，链官网 www.yes-tek.com）· 订单短号 · 状态徽标「待支付」
│
├─ 【全宽主卡 · 置顶】
│     支付卡：[支付二维码 200×200 白底] [价格 · 订单号 · 截止 · 倒计时]
│
├─ 两列网格（≥820px 双列，<820px 单列）
│   ├─ 左列（1.3fr）凭证卡：封面 112×200 + 标题 + 头像/作者/点赞/发布时间 + 用途说明
│   └─ 右列（1fr）  免费卡：小程序码 + 三步操作 / 或文字引导卡
│
├─ 【全宽套餐卡 · 仅支付态】
│     三档资源包（A/B/C，≥680px 三列，<680px 单列）+ 权益三条款 + 对话购买引导
│
└─ 页脚：免责声明 + 「二维码已内嵌，可保存本文件转发」

■ 套餐支付态（--stage package-pay）— 用户说「买套餐 X」后重渲同一 HTML
┌─ 顶栏：公司标识（logo+名称，链官网）· **套餐订单**短号 · 状态徽标「待支付 · 套餐」
│
├─ 【全宽主卡】套餐支付卡：[套餐订单自己的支付码] [套餐价 · 订单号 · 截止 · 支付到账
│     (granted) · 倒计时 · notice 三条款(.note)]——与支付卡同构，多「到账」与「条款」两行
│
├─ 两列网格：仅当有视频订单（--in 为 /api/order 响应）时保留；纯套餐页（--in 即
│   /api/package 响应）**不渲染**——钱包/批量流没有凭证可证
│
├─ 【全宽套餐卡】：仍渲染，**高亮正在支付的档**（accent 描边），换档只需再说一声
│
└─ 页脚：免责声明（措辞随是否有视频卡变）

■ 交付态（--stage delivered）— 只有一张卡
┌─ 顶栏：公司标识（logo+名称，链官网）· 订单短号 · 状态徽标「解析完成」
│
├─ 【全宽合并卡 · 唯一卡片】
│     [封面 112×200] │ 解析完成标题 + 「已交付」徽标
│                    │ 视频标题（H1）
│                    │ 头像 · 作者 · 点赞 · 发布日期
│                    │ ────────────────
│                    │ 时长 · 体积 · 分辨率
│                    │ 本地文件路径 + 复制按钮
│                    │ 免责小字
│
└─ 页脚：免责声明（**不提二维码**——交付页没有任何二维码）
```

**为什么交付态要合并、且不放免费通道：**

- **合并**：「解析完成」和「封面凭证」本来是同一件事的两半——都在说明"后端确实处理了这条视频"。拆成两张卡，用户要在两块内容里找同一个文件路径。合并后封面在左、交付信息在右（`.pad.merged`），一条视线读到底。
- **去掉免费通道**：免费通道是**决策期**的备选方案。用户已经付完款、文件已经落盘，再推"不想付费可以走小程序"是纯噪音——他要的东西已经拿到了。顺带省掉小程序码 31.6KB 内嵌，交付页从 ~104KB 降到 ~61KB。
- **页脚措辞也要跟着变**：支付态说"二维码图片已内嵌"，交付态**不能说**——它一张二维码都没有。这是"页面上的每句话都必须在当前页面成立"的具体一例（同 §四 反模式；标题字段陷阱见 `rendering.md` §七）。

> 凭证卡下方**不再挂文案卡**。历史版本曾把 `preview.description` 当"免费提取的视频文案"展示并配复制按钮——这是**错误标注**：该字段是作者自带的话题标签串，不含任何口播内容，用户拿去当文案用是错的。且实测它与 `preview.title` **逐字符相同**，所以连标题都需要净化（见 `rendering.md` §七）。

支付卡内部横向两段（`flex-wrap`，窄屏自动折行为竖排）：

| 段 | 内容 | 伸缩 |
|---|---|---|
| 左 | 支付二维码（固定白底 200×200） | 固定 |
| 右 | 价格 · 订单号 · 截止时间 · 倒计时 | `flex:1`，`min-width:230px` |

> 主卡里**没有第三段**。历史版本曾在此挂一块「三条信任话术」（服务端已预检通过 / 解析失败自动退款 / 腾讯 CDN 原画直链），已随 ③ 原则一并移除——那是**说服性文案**，不是页面功能。

**为什么主行动不做成右列**：双列布局下，<820px 会塌成单列，右列内容整体沉到封面上方内容的**后面**——手机上支付卡就跑到最底了。全宽置顶让桌面与手机的阅读顺序完全一致：先看到要做什么，再看到做的是什么。

### 模板拼装顺序（改渲染器时注意）

`render_order.py` 的模板分成四块，拼装顺序被刻意设计成**不依赖替换次序**：

| 模板 | 用途 |
|---|---|
| `TPL` | 页面骨架，含 `__MAIN_CARD__` / `__GRID__` / `__PACK_CARD__` / `__FOOT__` / `__STAGE_PILL__` |
| `PAY_CARD` / `PACKAGE_PAY_CARD` / `DONE_CARD` | 全宽主卡（按 stage 三选一；package-pay 的码/价/订单号来自 `--package-order`） |
| `GRID` | 支付态下方的两列网格（凭证卡 + 免费卡）；**交付态与纯套餐页不渲染**（`free_grid()` 为 pay / package-pay 共用） |
| `PACK_CARD` | 套餐与权益卡（支付态与套餐支付态渲染；**交付态不渲染**），数据来自 `PACKAGES` 常量；package-pay 时高亮 `--package-order` 的档位 |
| `FREE_CARD_QR` / `FREE_CARD_TEXT` | 免费卡（有素材用码，缺素材降级文字） |

关键做法：卡片内的公共占位符（`__COVER__` / `__TITLE__` / `__AVATAR__` / `__AUTHOR__` / `__META_EXTRA__`）**在插入 TPL 之前**就用 `fill_common()` 填掉，主替换链只负责 5 个顶层占位符；`__MP_NAME__` 相反——**在所有卡片插入之后**才统一替换（放替换链最前会被后插入的 `__GRID__` 逃过，就是下面反例的形状）。

> **反例（不要写回去）**：先 `.replace("__MAIN_CARD__", …)` 再 `.replace("__GRID__", …)`，同时又在末尾统一替换 `__COVER__` 之类——`__GRID__` 是最后插入的，它内部的占位符会**逃过**前面的替换，页面残留 `__COVER__`。这种写法必须靠"第二遍收尾替换"补救，顺序一改就出 bug。

末尾有**安全网**：任何残留的 `__XXX__` 占位符都会打印 `[warn]` 到 stderr，而不是静默写进 HTML。

## 二、二维码可扫性验证（改动渲染后必跑）

改动了二维码生成参数（`box_size` / 纠错级别 / 页面显示尺寸）后，**必须真扫一遍**，不能只看「长得像二维码」。

验证方法：从 HTML 里抠出内嵌的 PNG data URI，用 `cv2.QRCodeDetector` 解码，并**按页面实际 CSS 显示尺寸降采样后再解一次**——这一步模拟手机摄像头所见的像素密度，是真正的判据。

实测记录（样例订单，`code_url` 33 模块）：

| 项目 | 值 |
|---|---|
| 内嵌 PNG | 328×328 px（box_size=8，border=4），1.5 KB |
| 极性 | 静区均值 255 → 白底黑码，正确 |
| 内容比对 | 解码结果与 `code_url` 逐字符一致 |
| 页面显示 | 200px → 每模块 4.9px |

> **注意 cv2 的假阴性**：尺寸扫描中 150/328/400px 报解码失败，但 120/170/190/210/240/280/500/600px 均成功——**失败是非单调的**，这是 `cv2.QRCodeDetector` 内部自动缩放的重采样假象，不是二维码本身的问题。真机微信的容差比它宽得多。判定准则：**以「页面显示尺寸下解出且内容一致」为准**，不要因为某个尺寸失败就改动参数。

**安全下限**：显示尺寸下每模块 ≥ 3px。当前 200px / 33 模块 = 4.9px/模块，有余量。若未来 `code_url` 变长（矩阵更密），需同步提高 `.qr img` 的显示尺寸。

## 三、价格与名称的单一事实源（改价 / 改名流程）

套餐价目与小程序名定义在 `render_order.py` 顶部常量，**别处一律引用、不抄写**：

| 常量 | 内容 | 对外出口 |
|---|---|---|
| `PACKAGES` | 三档价格 / 单条折算 / 权益条目 | `render_order.py --dump-packages`（JSON；纯数据出口，**不需要** qrcode/pillow） |
| `MP_NAME` | 小程序名《越思工具》 | 模板内 `__MP_NAME__` 占位符（所有卡片插入后统一填入） |
| `COMPANY_NAME` / `COMPANY_URL` | 公司品牌「越思科技 Yes-Tek」与官网 | 顶栏 `<a class="brand">`（logo+名称，新窗口打开）；`FREE_ALT` 搜索关键词同源 |

对话侧要报价（B 轨套餐价目一行、402 后推荐套餐）时，跑 `--dump-packages` 取数，**不凭记忆写**。文档（SKILL.md / finder.md / api.md）只指向 dump，不出现具体价目数字。

**改价流程**：真实计费在服务端（下单响应的 `amount_cents` 才是用户实付）——先改服务端，再改 `PACKAGES`，然后跑校验：

```bash
python "$SKILL_DIR/scripts/check_consistency.py"
```

校验三件事：① 全库书名号名称与 `MP_NAME` 一致（faq / rendering / SKILL 等处的引用不许各说各话）；② `__MP_NAME__` 占位符不出现在其他脚本里（防替换链遗漏；文档以反引号提及属说明，不算）；③ `PACKAGES` 里的价目数字没有抄写进任何文档（防漂移）。退出码 0 = 一致。

**改名流程**：改 `MP_NAME` 一处（模板自动跟随）→ `check_consistency.py` → `rm -rf scripts/__pycache__`（旧字节码里也留着旧字符串）。名称在文档中的出现位置清单见 `assets/README.md`。

公司品牌「越思科技 Yes-Tek」已抽成 `COMPANY_NAME` / `COMPANY_URL` 常量：顶栏展示与 `FREE_ALT` 的搜索关键词都引用它，改品牌只动常量一处。顶栏 logo 是本地素材 `assets/company-logo.png`，base64 内嵌（获取与降级行为见 `assets/README.md`）。

## 四、反模式（页面结构与实现相关）

| 反模式 | 为什么不行 |
|---|---|
| 把支付卡放进双列网格的右列 | <820px 塌成单列后支付卡沉到最底，手机上要滚两屏才看到主行动 |
| **交付态仍保留免费通道卡** | 用户已付款、文件已落盘，再推"不想付费可以走小程序"是噪音——他要的东西拿到了；还白搭 31KB 小程序码内嵌 |
| **把「解析完成」和「封面凭证」拆成两张卡** | 两者都在说"后端确实处理了这条视频"，是同一件事的两半；拆开后用户要在两块内容里找同一个文件路径 |
| **两阶段共用同一套页脚措辞** | 支付态说"二维码已内嵌"是对的，交付态一张二维码都没有，那句话就成了假陈述 |
| **在支付卡里贴信任话术（预检通过 / 失败退款 / 原画直链）** | 用户已经在支付页、已经准备付款，卖点不改变动作；话术只在用户主动发问时于对话侧给出 |
| **把套餐区塞进支付卡或交付态** | 支付卡只承载一个动作（套餐卡独立放网格下方）；交付态用户已拿到文件，定价信息是噪音 |
| **在免费卡里写「付费通道是…」的对比话术** | 同一批主张的第二个出口，删了主卡却在免费卡留着等于没删；且用户点开免费卡说明他要的就是免费 |
| **封面做成大 hero 占据首屏** | 封面只是"后端确实解析到了"的凭证，把主行动挤下去是本末倒置 |

运行时行为类反模式（直链交付、ASCII 码、极性、`/status` fetch 等）见 `rendering.md` §八。

## 五、可选后端改进

给 `/api/order/:id/status` 加 `Access-Control-Allow-Origin: *`，页面即可自行刷新状态，省掉对话侧二次渲染。在未加之前，一律按「对话侧驱动」实现（`rendering.md` §五）。
