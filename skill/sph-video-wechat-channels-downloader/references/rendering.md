# 渲染与交付（rendering）

本文件规定：下单后**怎么把结果交给用户**。回答的是「输出形态」问题，不改变任何业务规则。

## 一、为什么需要它

下单成功后需要传达的是**三件性质完全不同的事**：

| 内容 | 性质 | 用户动作 |
|---|---|---|
| 标题/作者/点赞/封面 | 信息 | 看一眼，判断是不是要的 |
| 免费小程序通道 | 备选方案 | 记住或忽略 |
| 支付二维码 + 价格 + 截止时间 | **行动指令** | 立刻扫码 |

把它们压成一条 Markdown 文字流，用户要在一屏文字里找二维码、判断哪个是主行动、还要在手机上和对话窗口之间来回切。**信息层级塌陷**，扫码这一步的转化会明显掉。

因此：**先决定形态，再决定说什么。**

## 二、双轨决策（先判轨道，再渲染）

```
有「文件预览面板」能力（present_files / 富客户端）？
├─ 有 → A 轨：生成单文件自包含 HTML，用 present_files 打开；对话侧只留 3 行
└─ 无 → B 轨：不打印 ASCII 二维码；渲染 PNG 到本地并给绝对路径；对话侧给精简文本
```

### A 轨 · 富客户端（WorkBuddy / 带预览面板的 IDE）

```bash
# 1) 下单响应落盘（原始 JSON，别自己裁剪字段）
#    POST /api/order 的完整响应 → <workdir>/order_response.json
# 2) 渲染（$PY = ensure_deps.py --python 的输出，勿用裸 python）
"$PY" "$SKILL_DIR/scripts/render_order.py" \
  --in   <workdir>/order_response.json \
  --url  "<原始分享短链>" \
  --stage pay \
  --out  <workdir>/sph-downloads/<净化标题>.html
# 3) present_files 打开该 HTML
```

解析完成后再渲染一次，替换为交付态：

```bash
curl -sS "https://sph.yes-tek.com/api/order/<id>/deliver?token=<token>" -o <workdir>/deliver.json
"$PY" "$SKILL_DIR/scripts/ensure_ffmpeg.py" --probe "<mp4>" > <workdir>/probe.json

"$PY" "$SKILL_DIR/scripts/render_order.py" \
  --in <workdir>/order_response.json --url "<原始短链>" \
  --stage delivered --deliver <workdir>/deliver.json --probe <workdir>/probe.json \
  --out <workdir>/sph-downloads/<净化标题>.html
```

**对话侧只留 3 行**（模板与要求见 `SKILL.md` 第 3 节 A 轨；其余交给页面）。

### B 轨 · 纯终端（无预览面板）

- **不再默认打印 ASCII 二维码**。终端二维码的失败率远高于成功率：等宽字体行高非正方、自动折行、深色主题反色，三者任一都足以让码扫不出来。`qr.py` 已做三重兜底（border=4 / `--invert` / 超宽降级 PNG），但那是**补救**，不是**默认**。
- 改为：渲染 PNG 到本地 → 输出**绝对路径**，让用户用系统图片查看器打开（手机扫屏幕上的图片，成功率远高于扫终端字符画）。
- 同时给出订单号、付款截止时间、价格三行文本，便于用户手动核对。

```bash
"$PY" "$SKILL_DIR/scripts/qr.py" "<code_url>" --png "<workdir>/sph-downloads/支付二维码.png"
# 输出：<workdir>/sph-downloads/支付二维码.png
```

- 仅当用户**明确要求**「在终端里显示二维码」时才走 `"$PY" "$SKILL_DIR/scripts/qr.py" "<code_url>" --invert`。

## 三、二维码极性铁律（一票否决级）

> **屏幕扫码必须白底黑码。** 页面外壳可以跟随深浅主题，但二维码**必须画在固定的白色卡片上**，绝不跟随深色主题反色。

微信扫码对反色码的容差极低。`render_order.py` 中用 `.qr{background:#fff}` 强制白底，且 PNG 由 `qrcode.make_image(fill_color="black", back_color="white")` 生成——**不要**为了「页面统一」把二维码改成深色背景浅色模块。终端轨道才需要 `--invert`（因为终端字符是浅色、底色是深色，极性天然相反），HTML 里不存在这个问题。

## 四、单文件自包含（硬约束）

HTML 必须**不依赖任何外部资源**：

| 资源 | 处理 | 原因 |
|---|---|---|
| 封面图 | 压缩到 ≤900px 宽、JPEG q82、base64 内嵌 | 腾讯 CDN 有签名与防盗链，直接 `<img src="远程URL">` 会白图 |
| 作者头像 | 压缩到 ≤120px、base64 内嵌 | 同上（`wx.qlogo.cn`） |
| 支付二维码 | PNG base64 内嵌，**不做有损压缩** | 二维码压成 JPEG 会产生振铃伪影，可能扫不出 |
| 小程序码 | PNG base64 内嵌 | 同上 |

结果：单文件 60~70KB，可离线打开、可转发、可存档，不受预览面板 CSP 与网络影响。

`--no-remote` 开关：完全离线/沙箱环境下跳过远程拉取，封面降级为占位文字。

## 五、小程序码素材约定

> **小程序名 = 越思工具**，且它**散落在 4 个文件**（SKILL.md / 本文件 / render_order.py / assets/README.md）。改名时必须同步全部，否则会出现「顶栏写一个名、引导用户搜索另一个名」的错位。完整清单见 `assets/README.md`。

- 放置路径：`<skill>/assets/miniprogram-qr.png`
- 通过 `--miniprogram-qr <path>` 可覆盖
- **文件不存在时自动降级**为文字引导卡（「微信 → 发现 → 小程序 → 搜索《越思工具》」+ 一键复制分享链接），而不是画一个假码。
- **绝不要**用普通二维码冒充小程序码：普通二维码无法唤起小程序，用户扫了会得到错误结果，比不显示更糟。小程序码只能从微信公众平台生成，需人工放置。

### 素材必须先过 `prep_mp_qr.py`，不要直接丢文件

外来的小程序码（公众平台下载、截图二次处理）有两个高频缺陷，直接放进 `assets/` 会埋雷：

| 缺陷 | 后果 | 实测 |
|---|---|---|
| **静区被裁掉** | 静区不足是扫码失败的首要原因，**比模块密度更致命** | 一张 258×258 的截图，图案撑到 5~253，静区仅 4px ≈ **0.6 模块**（规范下限 4 模块） |
| **是 JPEG 而非 PNG** | `png_data_uri()` 是**原样读字节**、不做转码，却声明 `data:image/png`；JPEG 字节配 PNG 声明不可靠，且振铃伪影干扰码点 | 常见于截图/转发链 |

```bash
"$PY" "$SKILL_DIR/scripts/prep_mp_qr.py" <输入图片> [--out <路径>] [--modules 37] [--quiet 4]
```

脚本：解码 → 按 `--quiet` 模块补足白边 → **真转码**为 PNG（`optimize=True`，无损）。并打印体检报告与建议显示尺寸。`--modules` 是码直径包含的模块数（微信小程序码常见 37~41），宁可静区略大不要不够。

### 显示尺寸必须与素材分辨率匹配

`.free .qr img` 的宽度**不是随便定的**，要与素材边长对齐，否则浏览器插值放大反而糊：

```
CSS 显示尺寸 × 2（retina）  ≤  素材边长   →  无插值放大，最清晰
```

当前素材 303×303 → 显示 **150px**（retina 300px ≤ 303px）。**换素材后必须同步改这个值**，否则会出现"素材更清晰了但显示更糊"的反直觉结果。

右列（`1fr` ≈ 370px 内宽）可容纳的二维码块上限约 **180px**，超过会挤压操作步骤列导致折行。

### 替换后的审计（不能只看"图在页面上"）

替换素材后除重渲染外，必须验证**内嵌资源的声明与实际字节一致**：

```python
# data:image/png 的资源，实际字节必须以 PNG 魔数 \x89PNG\r\n\x1a\n 开头
# 若声明 png 而字节是 \xff\xd8\xff（JPEG）→ 素材没过 prep_mp_qr.py
```

**注意按尺寸/索引定位素材**：一个页面里通常有 4 张内嵌图（支付二维码 PNG / 封面 JPEG / 头像 JPEG / 小程序码 PNG），按固定索引取会**张冠李戴**——按边长识别（如 303×303）才可靠。

## 六、状态推进归对话侧（重要）

后端 `GET /api/order/:id/status` **未返回 CORS 头**（已实测）。因此：

- 页面内的 JS **无法**跨域轮询支付状态。不要在页面里写 `fetch(statusUrl)` 然后指望它工作——会静默失败。
- 页面的 JS 只做**本地倒计时**（纯时间运算，无需网络）；到期后**不给任何提示**，整块倒计时收起（截止时间仍有上方「付款截止」行兜底）。
- **状态推进由对话侧驱动**：Agent 用 `poll.py` 后台轮询 → 拿到 `resolved` → 重新渲染为 `--stage delivered` 覆盖同一个 HTML 文件。用户看到的页面自动变成交付态。

> 可选后端改进（非本技能可独立完成）：给 `/status` 加 `Access-Control-Allow-Origin: *`，页面即可自行刷新状态，省掉二次渲染。在未加之前，一律按上述「对话侧驱动」实现。

## 七、交付物：给本地路径，不给 CDN 直链

> **默认交付物是「本地那个文件在哪」，不是一条会过期的 URL。**

服务端**不留存视频文件**。CDN 直链只是腾讯侧的带签名临时地址，会过期、不可沉淀、用户也存不住——把它当作交付物展示，等于把一个随时失效的中间态当成最终成果推给用户。

用户真正需要的是：**下载已经完成了，文件在我的硬盘上，路径是这一条。** 所以交付态主卡展示的是本地 mp4 绝对路径 + 一键复制。

| | 默认 | 说明 |
|---|---|---|
| 本地文件路径 | **展示（主交付物）** | `--local-path`，绝对路径，配复制按钮 |
| 媒体信息（时长/体积/分辨率） | 展示 | 来自 `ffprobe` |
| CDN 直链 | **不展示** | 需要时才加 `--show-cdn-link` |

**保留 `--show-cdn-link` 的原因**：极少数场景仍需要直链（例如用户要把同一文件下到另一台机器、或导入网盘离线）。这是**逃生舱口**，不是默认路径。加了该开关时，页面会额外标注「带签名、会过期、服务端不留存」，避免用户误以为它是一个可长期保存的地址。

**对话侧的对应口径**：不要再把直链贴进对话。给「时长 / 体积 / 本地绝对路径」三行。`deliver` 接口仍要调用（它是解析完成与取到体积的凭据），只是结果不进用户可见层。

## 八、版式结构（A 轨）

**两条层级原则：**

**① 主行动永远在全宽顶部。** 用户来这里的目的是「付款/取货」，不是「读封面」。把二维码压在封面之后，等于逼用户扫读完两屏才看到主行动——层级塌陷又回来了。

**② 封面是凭证，不是主角。** 封面高度固定 **200px（与支付二维码等高）**，横向排列（9:16 封面 → 112×200）。它只需证明「后端确实解析到了这条视频、下载服务是通的」，不该占据首屏。

**③ 页面只放「用户要判断/要行动」的东西，不放元数据、不放话术。** 判据一句话：*这条信息会不会改变用户的下一步动作？* 不会的就不进页面。这条规则具体淘汰掉四类东西——

| 淘汰对象 | 为什么 |
|---|---|
| 话题标签串 | 作者的检索元数据，与用户决策无关 |
| 把标签串当"文案"的复制块 | 错误标注 + 重复展示 |
| **说服性话术**（预检通过 / 失败退款 / 原画直链 / 免费通道对比） | 用户已经在页面上、已经准备付款了，此时再贴卖点不改变动作，只是噪音 |
| 任何形式的原始字段倾倒 | 把接口返回直接糊到页面上 |

**话术不是删掉，是挪到它该在的地方**：对话侧。用户**主动问**"会不会白花钱""和免费工具有什么区别"时才回答（口径见 `references/faq.md`）。页面负责让已经决定的人快速完成动作；对话负责让还没决定的人获得答案。两者不要混。

**④ 两个阶段的形状不同，不要套同一个骨架。**

```
■ 支付态（--stage pay）
┌─ 顶栏：品牌名 · 订单短号 · 状态徽标「待支付」
│
├─ 【全宽主卡 · 置顶】
│     支付卡：[支付二维码 200×200 白底] [价格 · 订单号 · 截止 · 倒计时]
│
├─ 两列网格（≥820px 双列，<820px 单列）
│   ├─ 左列（1.3fr）凭证卡：封面 112×200 + 标题 + 头像/作者/点赞/发布时间 + 用途说明
│   └─ 右列（1fr）  免费卡：小程序码 + 三步操作 / 或文字引导卡
│
└─ 页脚：免责声明 + 「二维码已内嵌，可保存本文件转发」

■ 交付态（--stage delivered）— 只有一张卡
┌─ 顶栏：品牌名 · 订单短号 · 状态徽标「解析完成」
│
├─ 【全宽合并卡 · 唯一卡片】
│     [封面 112×200] │ 解析完成标题 + 「已交付」徽标
│                    │ 视频标题（H1）
│                    │ 头像 · 作者 · 点赞 · 发布日期
│                    │ ────────────────
│                    │ 时长 · 体积 · 分辨率
│                    │ 本地文件路径 + 复制按钮
│                    │ 免责小字
│
└─ 页脚：免责声明（**不提二维码**——交付页没有任何二维码）
```

**为什么交付态要合并、且不放免费通道：**

- **合并**：「解析完成」和「封面凭证」本来是同一件事的两半——都在说明"后端确实处理了这条视频"。拆成两张卡，用户要在两块内容里找同一个文件路径。合并后封面在左、交付信息在右（`.pad.merged`），一条视线读到底。
- **去掉免费通道**：免费通道是**决策期**的备选方案。用户已经付完款、文件已经落盘，再推"不想付费可以走小程序"是纯噪音——他要的东西已经拿到了。顺带省掉小程序码 31.6KB 内嵌，交付页从 ~104KB 降到 ~61KB。
- **页脚措辞也要跟着变**：支付态说"二维码图片已内嵌"，交付态**不能说**——它一张二维码都没有。这是"页面上的每句话都必须在当前页面成立"的具体一例（同 §十 的字段陷阱）。

> 凭证卡下方**不再挂文案卡**。历史版本曾把 `preview.description` 当"免费提取的视频文案"展示并配复制按钮——这是**错误标注**：该字段是作者自带的话题标签串，不含任何口播内容，用户拿去当文案用是错的。且实测它与 `preview.title` **逐字符相同**，所以连标题都需要净化（见 §九）。

支付卡内部横向两段（`flex-wrap`，窄屏自动折行为竖排）：

| 段 | 内容 | 伸缩 |
|---|---|---|
| 左 | 支付二维码（固定白底 200×200） | 固定 |
| 右 | 价格 · 订单号 · 截止时间 · 倒计时 | `flex:1`，`min-width:230px` |

> 主卡里**没有第三段**。历史版本曾在此挂一块「三条信任话术」（服务端已预检通过 / 解析失败自动退款 / 腾讯 CDN 原画直链），已随第 ③ 条原则一并移除——那是**说服性文案**，不是页面功能。

**为什么主行动不做成右列**：双列布局下，<820px 会塌成单列，右列内容整体沉到封面上方内容的**后面**——手机上支付卡就跑到最底了。全宽置顶让桌面与手机的阅读顺序完全一致：先看到要做什么，再看到做的是什么。

### 模板拼装顺序（改渲染器时注意）

`render_order.py` 的模板分成四块，拼装顺序被刻意设计成**不依赖替换次序**：

| 模板 | 用途 |
|---|---|
| `TPL` | 页面骨架，含 `__MAIN_CARD__` / `__GRID__` / `__FOOT__` / `__STAGE_PILL__` |
| `PAY_CARD` / `DONE_CARD` | 全宽主卡（按 stage 二选一） |
| `GRID` | 支付态下方的两列网格（凭证卡 + 免费卡）；**交付态不渲染** |
| `FREE_CARD_QR` / `FREE_CARD_TEXT` | 免费卡（有素材用码，缺素材降级文字） |

关键做法：卡片内的公共占位符（`__COVER__` / `__TITLE__` / `__AVATAR__` / `__AUTHOR__` / `__META_EXTRA__`）**在插入 TPL 之前**就用 `fill_common()` 填掉，主替换链只负责 5 个顶层占位符。

> **反例（不要写回去）**：先 `.replace("__MAIN_CARD__", …)` 再 `.replace("__GRID__", …)`，同时又在末尾统一替换 `__COVER__` 之类——`__GRID__` 是最后插入的，它内部的占位符会**逃过**前面的替换，页面残留 `__COVER__`。这种写法必须靠"第二遍收尾替换"补救，顺序一改就出 bug。

末尾有**安全网**：任何残留的 `__XXX__` 占位符都会打印 `[warn]` 到 stderr，而不是静默写进 HTML。

## 九、标题净化与标签处理（字段陷阱）

后端 `preview` 里有两个字段，**实测逐字符相同**：

```
preview.title       = '真正标题  #标签1 #标签2 #标签3 … '
preview.description = '真正标题  #标签1 #标签2 #标签3 … '   ← 与上面完全一致
```

也就是说，**`title` 实际上是「标题 + 尾部话题标签串」的整条描述**，`description` 没有任何额外信息。

三条处理规则：

| 字段 | 处理 | 理由 |
|---|---|---|
| `preview.title` | 过 `clean_title()` 剥掉尾部标签串再展示；同时用于 `<title>`、文件名、对话侧 | 标签串占了 H1 就等于把标题换成了一串 hashtag |
| `preview.description` | **不进页面**；仅当用户明确"要标签/找选题"时用 `extract_tags()` 单独给出标签数组 | 它是作者的检索元数据，不是文案也不是标题 |
| 两者都不做 | 不标成"文案/逐字稿"、不配复制按钮 | 不含口播内容，用户拿去当文案用是错的 |

`clean_title()` 的实现要点：

- 正则 `(?:\s*#[^\s#]+)+\s*$` 只剥**尾部连续标签串**，不误伤标题中部的 `#`
- 剥完为空（标题本身就是一串标签，如 `#每日分享 #干货`）→ **原样返回**，不塌成空字符串
- 无空格连写（`标题#标签`）也能剥
- 整串没标签 → 原样返回

文件名/输出路径统一用净化后的标题，避免 `#` 进文件名（Windows 下虽合法，但复制粘贴和 URL 场景容易断）。

## 十、反模式

| 反模式 | 为什么不行 |
|---|---|
| 把支付卡放进双列网格的右列 | <820px 塌成单列后支付卡沉到最底，手机上要滚两屏才看到主行动 |
| **交付态仍保留免费通道卡** | 用户已付款、文件已落盘，再推"不想付费可以走小程序"是噪音——他要的东西拿到了；还白搭 31KB 小程序码内嵌 |
| **把「解析完成」和「封面凭证」拆成两张卡** | 两者都在说"后端确实处理了这条视频"，是同一件事的两半；拆开后用户要在两块内容里找同一个文件路径 |
| **两阶段共用同一套页脚措辞** | 支付态说"二维码已内嵌"是对的，交付态一张二维码都没有，那句话就成了假陈述 |
| **在支付卡里贴信任话术（预检通过 / 失败退款 / 原画直链）** | 用户已经在支付页、已经准备付款，卖点不改变动作；话术只在用户主动发问时于对话侧给出 |
| **在免费卡里写「付费通道是…」的对比话术** | 同一批主张的第二个出口，删了主卡却在免费卡留着等于没删；且用户点开免费卡说明他要的就是免费 |
| **把 `preview.description` 标成"视频文案"并配复制按钮** | 它是话题标签串、不含口播内容；用户拿去当文案用是错的。且与 `title` 逐字符相同，展示两份等于重复 |
| **直接把 `preview.title` 当标题展示** | 它尾部焊着标签串，H1 会变成一串 hashtag |
| **把 CDN 直链当交付物展示** | 服务端不留存文件，直链会过期、存不住；用户要的是「本地文件在哪」 |
| **封面做成大 hero 占据首屏** | 封面只是"后端确实解析到了"的凭证，把主行动挤下去是本末倒置 |
| 页面里 JS 直接 fetch `/status` | 后端无 CORS，必然静默失败，给人「状态不更新」的错觉 |
| 二维码跟随深色主题反色 | 微信扫码容差低，大概率扫不出 |
| 用普通二维码冒充小程序码 | 唤起不了小程序，用户拿到错误结果 |
| 远程 URL 直接 `<img src>` | 签名失效/防盗链 → 白图 |
| 二维码走 JPEG 压缩 | 振铃伪影导致误码 |
| 终端里强行打印 ASCII 码当默认 | 折行/反色/行高非正方，失败率高于成功率 |
| 对话侧仍输出大段 Markdown 复述页面内容 | 双份信息，且回到「层级塌陷」的原点 |

## 十一、二维码可扫性验证（改动渲染后必跑）

改动了二维码生成参数（`box_size` / 纠错级别 / 页面显示尺寸）后，**必须真扫一遍**，不能只看「长得像二维码」。

验证方法：从 HTML 里抠出内嵌的 PNG data URI，用 `cv2.QRCodeDetector` 解码，并**按页面实际 CSS 显示尺寸降采样后再解一次**——这一步模拟手机摄像头所见的像素密度，是真正的判据。

实测记录（样例订单，`code_url` 33 模块）：

| 项目 | 值 |
|---|---|
| 内嵌 PNG | 328×328 px（box_size=8，border=4），1.5 KB |
| 极性 | 静区均值 255 → 白底黑码，正确 |
| 内容比对 | 解码结果与 `code_url` 逐字符一致 |
| 页面显示 | 200px → 每模块 4.9px |

> **注意 cv2 的假阴性**：尺寸扫描中 150/328/400px 报解码失败，但 120/170/190/210/240/280/500/600px 均成功——**失败是非单调的**，这是 `cv2.QRCodeDetector` 内部自动缩放的重采样假象，不是二维码本身的问题。真机微信的容差比它宽得多。判定准则：**以「页面显示尺寸下解出且内容一致」为准**，不要因为某个尺寸失败就改动参数。

**安全下限**：显示尺寸下每模块 ≥ 3px。当前 200px / 33 模块 = 4.9px/模块，有余量。若未来 `code_url` 变长（矩阵更密），需同步提高 `.qr img` 的显示尺寸。

## 十二、与其他步骤的接口

- 本文件只改**步骤 3（展示预览 + 支付）**与**步骤 5（取货交付）的输出形态**。
- 业务规则一律不变：预检门、价格、退款语义、免费通道引导、免责声明的**内容**照旧，只是**载体**从 Markdown 变成页面/PNG。
- `render_order.py` 只读不写订单状态，不发起支付，不下载视频——**纯渲染器**，不与 `poll.py` / `qr.py` 的职责重叠。
